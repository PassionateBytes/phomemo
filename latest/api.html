    API reference#

    The phomemo package, as installed from PyPI.

    Printer#

    High-level async printer client.

    The Printer class is the primary developer-facing API. It composes the transport, protocol, event, and imaging modules into a single coherent interface for controlling Phomemo thermal printers.

    Typical usage:

    from phomemo import Printer, Density

async with Printer("m08f", "AA:BB:CC:DD:EE:FF") as printer:
    await printer.connect()

    # Check device state before printing
    info = await printer.query_device_info()
    print(f"Battery: {info.battery}%, Lid: {info.lid}, Paper: {info.paper}")

    # Wait for a sheet, print, feed it out
    await printer.wait_for_ready()
    await printer.print_image("photo.png", density=Density.MEDIUM)
    await printer.eject_paper()

    async connect(discovery_timeout=5.0)[source]#

    Connect to the printer.

    The transport always receives a BLEDevice from a live scan: BlueZ can only connect to a device it has seen advertising recently, so a bare MAC address is resolved through a targeted scan first. Without an address, scans for a nearby device whose advertised name matches the profile’s ble_name_pattern, connects to it and keeps its address for later connects; several matches are refused rather than picking one.

    Parameters:

    discovery_timeout (float) – Scan duration in seconds, for both name-based discovery and MAC resolution. Ignored if a BLEDevice was provided at instantiation.

    Raises:

    • ConnectionError – If the connection fails, if a name scan finds no matching device or several, or if the given MAC address is not seen within discovery_timeout.

    • RuntimeError – If already connected.

    Return type:

    None

    async eject_paper(max_feeds=64, step_rows=120, ahead=2, feed_seconds=0.7, clear_rows=160)[source]#

    Feed the sheet out until the sensor reports it gone, then clear the rollers.

    Feeds of step_rows (15mm by default) are kept ahead deep in the printer’s queue so the motor runs without pauses: one more goes out whenever feed_seconds (about one section at the measured feed speed) pass without the paper-absent event. On the event, one feed of clear_rows pushes the sheet out of the rollers. A sheet already past the sensor, or a printer that does not answer the initial query, gets three feeds of clear_rows blind.

    Parameters:

    • max_feeds (int) – Maximum number of feeds before giving up (about 1m).

    • step_rows (int) – Rows per feed.

    • ahead (int) – Feeds queued before waiting for the sensor event.

    • feed_seconds (float) – Wait per feed for the sensor event before queuing the next one; longer than the feed itself stalls the motion, shorter queues ahead of the motor.

    • clear_rows (int) – Rows fed once the sensor is clear.

    Returns:

    True once the sheet has left the sensor, False if it is still present after max_feeds feeds.

    Return type:

    bool

    async wait_for_ready(timeout=60.0, poll=0.5, settle=3.0, mute_threshold=3)[source]#

    Block until a sheet is loaded and seated at the print head.

    Polls check_ready so a caller can start a page job and let the user insert the sheet afterwards. The paper sensor reports the sheet as soon as its edge arrives; the feed motor keeps pulling for about two more seconds and then the printer repeats the paper-present event. settle waits for that repeat (capped) so raster data is not sent while the sheet is still moving.

    mute_threshold consecutive query timeouts mean the printer is in the error state left by a sheet overrun; the connection is dropped and re-established once, which clears it.

    Parameters:

    • timeout (float) – Maximum seconds to wait for a sheet.

    • poll (float) – Seconds between readiness checks.

    • settle (float) – Maximum seconds to wait for the feed to complete after the sheet is detected; 0 sends as soon as it is detected.

    • mute_threshold (int) – Consecutive query timeouts before a reconnect.

    Raises:

    TimeoutError – With the last readiness reason as message.

    Return type:

    None

    Profiles#

    Each profile captures the physical and protocol characteristics of a specific Phomemo printer model: print width, BLE UUIDs, timing constraints, and supported features. The profile system is extensible — add new models by registering a PrinterProfile instance via register_profile.

    Images and pages#

    Image preparation pipeline for thermal printing.

    Converts arbitrary images into 1-bit raster bitmaps suitable for Phomemo printers. The pipeline handles resizing, padding/cropping, grayscale conversion, and dithering.

    Bitmap format (from the M08F Protocol Reference): - 1 bit per pixel, packed into bytes. - 1 = black (ink on), 0 = white (no ink). - Most significant bit of each byte is the leftmost pixel. - Rows are sequential top-to-bottom.

    Events#

    Device event parsing for Phomemo printer notifications.

    All events arrive on the ff01 BLE characteristic as 1a <sub-type> <data> messages. Events can be spontaneous (triggered by physical state changes) or solicited (responses to 1f 11 XX queries). Both use the same 1a-prefixed format.

    Multiple 3-byte events can arrive concatenated in a single BLE notification. The parser consumes 3 bytes at a time.
